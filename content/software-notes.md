## 0. 一句话总览

软件工程研究的是: 怎样用工程化方法把软件从“想法”变成“可交付、可维护、质量可控的产品”。

整门课可以按这条线复习:

```text
软件危机
-> 软件过程模型
-> 需求工程
-> 软件设计
-> 编码实现
-> 软件测试
-> UML 与面向对象分析设计
-> 软件维护
-> 项目管理
```

考试常见不是让你写程序，而是问概念、比较、建模、设计原则、测试用例和项目管理计算。最重要的能力是: 看见一个系统场景，知道它处在软件生命周期哪一阶段，应该产出什么文档、用什么模型、怎么验证质量。

### 0.1 老师版范围地图

老师资料按 12 块组织:

### 0.2 老师特别强调的说法

- 软件工程主要研究软件开发的理论、方法和标准。
- 软件是程序、数据及相关文档的完整集合。
- 软件不是物理实体；软件开发和生产过程统一；软件不会随时间流逝老化，但维护期很长。
- [软件危机](?doc=deep-dive&anchor=software-crisis#reader)的表现包括质量难达标、成本进度难预测、维护困难、开发难管理、成本逐年上升。
- 错误观念包括“开发软件就是编程”“程序能运行开发就结束”“软件很容易修改”“增加人员可以加快进度”。
- IEEE 版软件工程定义关键词是系统的、规范的、可度量的工程化方法，覆盖开发、运行和维护全过程。
- [生命周期](?doc=deep-dive&anchor=software-crisis#reader)阶段在老师资料中写作: 需求分析、设计、实现、测试、维护；其中需求分析包括问题定义和可行性分析，设计包括概要设计和详细设计。
- 生命周期方法学可以简化或合并某些阶段，但不能完全取消阶段，也不能破坏瀑布模型自上而下的基本流程。
- 生命周期方法学特点: 分阶段计划、瀑布式开发模式、阶段技术审查和管理复审形成基线、各阶段采用结构化技术或面向对象技术。

### 0.3 需要按老师口径修正的地方

原讲义为了完整，包含了 SRS、敏捷、设计模式、项目估算等较多扩展内容。考试前应这样排序:

1. 先背老师资料里明确列出的定义、阶段、原则、工具和分类。
2. 再用完整讲义补理解，比如为什么瀑布适合需求稳定、为什么高内聚低耦合有利于维护。
3. 项目管理先背基本概念、软件配置、配置项、质量管理、配置管理、CMM、LOC、FP。复杂成本公式不是这份老师资料的重点。
4. 维护的可维护性因素，老师资料压成三个: 可理解性、可测试性、可修改性。完整讲义中的可移植性、可重用性可作为扩展。
5. 测试部分老师资料没有强调 V/W/H 模型和 α/β 测试，优先背测试目标、测试原则、单元/集成/系统/验收、自顶向下/自底向上、白盒黑盒方法。

### 0.4 老师资料最像会出题的点

- 问题定义: 明确要解决的问题究竟是什么。
- 可行性分析: 技术、操作、经济、法律四方面，形成可行性分析报告。
- [DFD](?doc=deep-dive&anchor=software-dfd#reader): 数据源点/终点、处理、数据存储、数据流线四种符号；箭头表示数据流，不是控制流。
- [数据字典](?doc=deep-dive&anchor=software-dfd#reader): DFD 中的数据流名称必须在 DD 中有对应定义；要保证完整性、一致性、正确性。
- 模块四个基本属性: 输入、输出、逻辑功能、内部数据。
- 模块化的目标: 降低复杂度、减少工作量；模块数量适中时总工作量最低。
- 信息隐藏和局部化: 降低接口复杂度，提高模块独立性。
- 良好结构化设计: 尽量使用数据耦合，少用控制耦合，限制公共耦合，坚决不用内容耦合。
- 总体设计步骤: 设想方案、选取合理方案、推荐最佳方案、功能分解、设计软件结构、数据设计、制定测试计划、书写文档。
- 详细设计工具: 程序流程图、盒图 NS 图、判定树、判定表。老师特别写了“要能够用盒图描写简单处理过程”。
- 结构化程序设计: 顺序、选择、循环三种基本控制结构；逐步求精；单入口单出口。
- [测试原则](?doc=deep-dive&anchor=software-testing#reader): 一般不测试自己设计的程序；测试输入要有预期输出；合法输入和非法输入都要测；测试数据作为 SCI 纳入文档管理；程序错误率与已发现错误数量成正比。
- 单元测试: 以模块为对象，代码审查是静态测试，动态测试根据测试用例运行程序；单元测试白盒为主，之后其他测试黑盒为主。
- 综合测试: 集成测试和系统测试；渐增式测试包括自顶向下和自底向上，分别需要桩模块和驱动模块。
- [OOA](?doc=deep-dive&anchor=software-ooa-ood#reader): 建立用例模型，确定类对象、属性、服务、结构、主题，建立动态模型。
- [OOD](?doc=deep-dive&anchor=software-ooa-ood#reader): 系统设计、类对象设计、数据设计、消息设计、人机交互设计。
- [维护](?doc=deep-dive&anchor=software-maintenance#reader)阶段文档: 软件问题报告和软件修改报告。

## 1. 软件工程概述

### 1.1 软件是什么

软件不是只有程序代码。软件是计算机系统中与硬件相互依存的另一部分，包括:

- 程序: 能运行的指令序列。
- 数据: 程序处理、保存、传输的信息。
- 相关文档: 需求、设计、测试、用户手册、维护说明等。

考试里如果问“软件的完整集合”，答案要包含“程序、数据及相关文档”，只写程序是不完整的。

### 1.2 软件的本质特性

- 复杂性: 软件规模大、状态多、逻辑关系复杂。
- 一致性: 软件要和现实业务、硬件平台、其他软件接口保持一致。
- 可变性: 用户需求、运行环境、业务规则都可能变化。
- 不可见性: 软件结构不像建筑那样可直接观察，理解和控制都更难。

这些特性解释了为什么软件开发不能只靠个人经验，而要靠过程、文档、评审、测试和管理。

### 1.3 软件危机

软件危机指软件开发中长期存在的成本超支、进度拖延、质量低、维护困难、难以满足用户需求等问题。

老师 2026 资料给出的软件危机表现更适合考试直接背:

- 软件质量难以达到用户要求，极易发生故障，可靠性差。
- 成本和进度难以预测，也难以控制。
- 软件维护困难。
- 软件开发工作难以管理。
- 软件成本逐年上升。

同时要会识别四个错误观念:

- 开发软件就是编程。
- 程序可以运行，软件开发就结束。
- 软件是灵活的，可以很容易修改。
- 增加人员可以加快进度。

常见原因:

- 对软件开发缺乏正确理论指导。
- 开发人员与用户沟通不足，需求理解偏差。
- 对软件开发过程缺乏整体认识，只重编码不重分析和设计。
- 对软件质量缺乏统一有效的评价标准。
- 需求变化频繁，而缺少变更控制。

软件工程就是为了解决软件危机而产生的工程化方法体系。

### 1.4 软件工程三要素

软件工程包括三个基本要素:

- 方法: 做需求、设计、测试、维护时采用的技术方法。
- 工具: 支持开发和管理的软件工具。
- 过程: 规定活动顺序、角色、产物、评审和管理方式。

如果题目问“软件工程核心”，通常要把这三者一起写出来。方法解决“怎么做”，工具提高效率，过程保证开发活动可控。

### 1.5 软件生命周期

软件生命周期是软件从提出到退役的全过程，常见阶段包括:

1. 可行性与计划阶段。
2. 需求分析阶段。
3. 设计阶段。
4. 实现阶段。
5. 测试阶段。
6. 运行和维护阶段。

每个阶段都有自己的主要产物。需求阶段产出需求规格说明 SRS，设计阶段产出设计规格说明，实现阶段产出代码，测试阶段产出测试计划、测试用例、测试报告，维护阶段产出维护申请、修改说明和回归测试记录。

老师 2026 资料的阶段划分要优先记成:

```text
需求分析（问题定义、可行性分析）
-> 设计（概要设计、详细设计）
-> 实现（编码）
-> 测试
-> 维护
```

如果考试问“生命周期方法学”，还要补一句: 某些阶段可以简化和合并，但不能完全取消，也不能破坏瀑布模型从上到下的流程。

### 1.6 软件工程基本原则

复习时可按“可控、可审查、可修改”理解:

- 用分阶段的生命周期计划严格管理。
- 坚持阶段评审，及时发现错误。
- 严格控制产品和文档的变更。
- 采用现代程序设计和工程技术。
- 软件结果应能被清楚审查。
- 开发小组人员少而精。
- 承认软件工程实践需要持续改进。

## 2. 软件过程模型

### 2.1 软件过程是什么

软件过程是组织或项目用来计划、管理、执行、监控和改进软件活动的一组过程集合。过程模型是对这些活动顺序和关系的抽象。

考试常问“某模型适用于什么情况”“优缺点是什么”“为什么某模型强调风险或文档”。

### 2.2 瀑布模型

瀑布模型按生命周期阶段顺序向下推进:

```text
可行性 -> 需求 -> 设计 -> 编码 -> 测试 -> 维护
```

特点:

- 阶段清晰，文档严格。
- 强调阶段评审和质量保证。
- 适合需求明确、变化少、规模和技术较稳定的项目。
- 缺点是反馈晚，需求变化时代价大，用户较晚看到可运行软件。

考点: 瀑布模型强调“严格顺序、阶段性、文档驱动、一次性交付”。

### 2.3 原型模型

原型是早期可运行或可演示的简化系统，用来帮助用户和开发人员理解需求。

适用场景:

- 需求不明确。
- 用户难以一次说清需求。
- 需要验证界面、交互或关键功能。

类型:

- 抛弃型原型: 用来澄清需求，之后丢弃。
- 演化型原型: 在原型基础上逐步演进成最终系统。

优点是有利于需求沟通；风险是用户可能误以为原型就是最终系统，或者原型结构差却被继续使用。

### 2.4 增量模型

增量模型把系统功能分成多个增量，每个增量都经历类似瀑布的分析、设计、实现、测试。

特点:

- 非整体一次性交付。
- 每个增量都能交付部分可用功能。
- 适合需求可分解、希望尽早交付核心功能的项目。

复习关键词: “逐步交付、分批实现、每个增量可运行”。

### 2.5 螺旋模型

螺旋模型把瀑布模型和原型模型结合起来，强调风险分析。

每一圈通常包括:

1. 确定目标、方案和约束。
2. 风险分析。
3. 工程实现。
4. 用户评审和下一轮计划。

适合大型、复杂、高风险项目。考试见到“风险驱动”，优先想到螺旋模型。

### 2.6 敏捷过程模型

敏捷强调快速反馈、持续交付和适应变化。敏捷宣言常见四句话:

- 个体和交互胜过过程和工具。
- 可以工作的软件胜过面面俱到的文档。
- 客户合作胜过合同谈判。
- 响应变化胜过遵循计划。

注意: 敏捷不是不要文档，而是不让文档压过可工作的软件和有效沟通。

### 2.7 迭代模型

迭代模型通过一轮轮循环不断完善系统。每一轮都可能包括需求、设计、实现、测试，只是范围逐步扩大或细节逐步清晰。

可以这样记:

- 原型解决需求不清。
- 增量解决分批交付。
- 螺旋解决风险控制。
- 迭代解决逐步演进。

## 3. 软件需求工程

### 3.1 需求工程的目标

需求工程要完整、准确、一致地描述目标系统应该做什么，以及在什么约束下做。需求工程不是只发生在开头，它会贯穿整个生命周期。

老师资料把需求分析前面的“问题定义”单独强调: 问题定义阶段的主要任务是明确要解决的问题究竟是什么。系统分析员要和用户项目负责人交谈、现场调研、写出问题描述，再和用户澄清不一致和模糊内容。

需求分析的任务:

- 确定系统要实现的功能、性能、接口、数据和约束。
- 建立数据模型、功能模型、行为模型。
- 定义系统逻辑模型。
- 编写软件需求规格说明 SRS。
- 适应和管理需求变更。

### 3.2 需求类型

- 功能需求: 系统必须提供什么服务。
- 性能需求: 响应时间、吞吐量、可靠性等。
- 领域需求: 来自业务领域的规则和约束。
- 接口需求: 与用户、硬件、其他系统的交互方式。
- 其他非功能需求: 安全、可用性、可维护性、可移植性等。

功能需求写“系统做什么”，非功能需求写“系统做得怎么样”。

### 3.3 可行性分析

可行性分析通常在需求工程初期进行，用来判断问题是否值得做、能否做。

四类可行性:

- 技术可行性: 技术、工具、人员能力是否支持。
- 经济可行性: 成本收益是否合理。
- 操作可行性: 用户是否能接受，是否符合业务流程。
- 法律可行性: 是否符合法律、合同、知识产权和安全要求。

考试简答题常直接问“四方面可行性”，要按这四类答。

### 3.4 需求工程活动

典型活动:

1. 可行性分析。
2. 需求获取。
3. 需求分析与建模。
4. 需求规格说明。
5. 需求评审。
6. 需求变更管理。

需求获取技术:

- 访谈: 适合深入了解用户想法。
- 会议: 适合统一多方观点。
- 问卷: 适合大范围收集信息。
- 场景分析: 通过模拟用户操作发现需求。
- 快速原型: 通过可见原型澄清需求。

### 3.5 软件需求规格说明 SRS

SRS 是需求阶段的核心文档。它描述系统应该做什么，不应该写入算法和程序实现细节。

SRS 的作用:

- 便于用户和分析人员沟通。
- 作为设计和开发的基础。
- 支持最终系统确认。
- 控制需求变更。
- 作为测试验收依据。

高质量 SRS 应具有:

- 正确性。
- 完整性。
- 一致性。
- 可行性。
- 可理解性。
- 可验证性。
- 可修改性。
- 可追踪性。

### 3.6 需求变更管理

需求变更不可避免，但必须受控。

常见机制:

- 需求基线: 已通过正式评审并受控的需求版本。
- 变更申请: 用户或项目成员提出变更。
- 影响分析: 分析对成本、进度、设计、代码、测试的影响。
- 变更审查: 决定是否接受。
- 变更记录: 保存修改过程，保证可追踪。

考试关键词“基线”通常指已经通过正式复审、可作为后续开发依据的文档或配置项。

## 4. 结构化需求分析

### 4.1 结构化分析的核心

结构化分析以数据为核心，围绕数据字典建立模型，常用三类模型:

- 数据模型: E-R 图。
- 功能模型: 数据流图 DFD。
- 行为模型: 状态转换图 STD。

结构化分析强调自顶向下、逐层分解，目标是建立系统逻辑模型，而不是物理实现模型。

### 4.2 E-R 图

E-R 图描述实体、属性和实体之间的关系，主要反映系统的数据静态结构。

常见元素:

- 实体: 现实世界中可区分的对象，如学生、订单。
- 属性: 实体的特征，如学号、姓名。
- 联系: 实体之间的关系，如学生选课。

如果题目问“哪个模型用于数据建模”，答案通常是 E-R 图。

### 4.3 数据流图 DFD

DFD 从数据流动角度描述系统逻辑功能。它描述数据从外部实体进入系统，经加工、存储，再输出的过程。

基本成分:

- 外部实体: 系统外部的数据源或数据终点。
- 加工: 对数据进行处理的功能。
- 数据流: 有方向的数据移动。
- 数据存储: 系统保存的数据。

注意: DFD 中箭头表示数据流，不表示控制流。

### 4.4 DFD 建模步骤

1. 确定系统边界和外部实体。
2. 画顶层 DFD，表现系统与外部环境的数据交换。
3. 对主要加工逐层分解，得到 0 层、1 层、2 层等。
4. 检查父图和子图平衡。
5. 配套编写数据字典。

父图与子图平衡是高频考点: 子图对外的输入输出数据流必须与父图中对应加工的输入输出一致。

### 4.5 DFD 常见错误

- 数据流没有名字。
- 加工只有输入没有输出，或只有输出没有输入。
- 数据存储直接连外部实体，中间没有加工。
- 外部实体之间直接连数据流。
- 父图和子图输入输出不平衡。
- 把控制条件画成数据流。

做 DFD 改错题时，先检查四类元素之间的连线是否合法，再检查分层平衡。

### 4.6 数据字典

数据字典定义 DFD 中出现的数据流、数据项、数据存储和加工说明。它让不同模型中的数据名称和含义保持一致。

常见内容:

- 数据流词条。
- 数据元素词条。
- 数据存储词条。
- 加工词条。

数据字典的作用是统一定义、消除歧义、保证完整性和一致性。

老师 2026 资料给出的数据字典检查标准:

- 完整性: DFD 中的数据流名称在 DD 中必须有对应名称。
- 一致性: DFD 中的数据流名与 DD 中定义的数据语义必须一致。
- 正确性: 数据定义要真实描述用户领域的数据、结构、文件等信息。

### 4.7 状态转换图 STD

状态转换图描述对象或系统在事件触发下如何从一种状态变为另一种状态。

关键概念:

- 状态: 对象在某时刻可观察的行为属性。
- 事件: 触发状态转换的事情。
- 转换: 由事件或条件触发的状态变化。
- 动作: 转换时执行的操作。

适合描述有明显状态变化的对象，如订单、借书记录、设备开关。

## 5. 软件设计基础

### 5.1 设计任务

软件设计把需求模型转换成可实现的软件结构。设计阶段回答“怎么做”，但还没有进入具体编码。

设计目标:

- 高内聚。
- 低耦合。
- 高可靠性。
- 高可维护性。
- 高可理解性。
- 高效率。

### 5.2 概要设计与详细设计

概要设计又称总体设计，关注系统整体结构:

- 软件体系结构设计。
- 模块划分。
- 数据设计。
- 接口设计。
- 人机界面设计。

详细设计关注模块内部:

- 算法。
- 局部数据结构。
- 控制流程。
- 过程描述。

简记: 概要设计决定“有哪些模块、模块怎么协作”，详细设计决定“模块内部怎么实现”。

### 5.3 软件体系结构

体系结构描述系统的整体组织方式、部件关系和控制数据流。

常见结构:

- 以数据为中心: 数据仓库或数据库居中，多个部件共享数据。
- C/S: 客户端请求服务，服务器响应。
- 多层架构: 表示层、业务逻辑层、数据层分开。
- 层次模型: 上层调用下层，下层提供服务。
- MVC: 模型 Model、视图 View、控制 Controller 分离。

体系结构设计是概要设计的核心。

### 5.4 模块化、抽象、信息隐藏

模块化是把复杂系统分解成一组模块。好处是降低复杂度、便于分工、测试和维护。

老师资料给出的模块定义更适合填空: 模块是具有输入、输出、逻辑功能、内部数据四个基本属性的指令集合。

抽象是忽略细节、抓住本质。比如只暴露接口，不暴露内部算法。

信息隐藏是把容易变化的设计决策隐藏在模块内部，外部只能通过接口访问。这样内部实现改变时，对外部影响更小。

局部化是把可能互相作用的过程和数据尽量放在一个模块内。信息隐藏和局部化的意义都在于降低模块接口复杂度，提高模块独立性。

### 5.5 模块独立性

模块独立性用两个指标衡量:

- 内聚: 模块内部各成分联系强度。越高越好。
- 耦合: 模块之间依赖强度。越低越好。

设计目标是高内聚、低耦合。

### 5.6 内聚类型

从低到高大致为:

- 偶然内聚: 不相关功能凑在一起。
- 逻辑内聚: 逻辑上相似功能放一起，由参数决定执行哪一个。
- 时间内聚: 同一时间段执行的操作放一起。
- 过程内聚: 按固定过程顺序执行的操作放一起。
- 通信内聚: 操作同一输入数据或产生同一输出数据。
- 顺序内聚: 一个成分输出是另一个成分输入。
- 功能内聚: 模块只完成一个明确功能。

功能内聚最好，偶然内聚最差。

### 5.7 耦合类型

从低到高大致为:

- 非直接耦合: 模块之间没有直接联系。
- 数据耦合: 只传递简单数据项。
- 特征耦合: 传递复合数据结构。
- 控制耦合: 传递控制信号影响对方逻辑。
- 公共耦合: 多个模块共享全局数据。
- 内容耦合: 一个模块直接访问或修改另一个模块内部。

内容耦合最差，应避免；数据耦合较好。

### 5.8 启发式设计规则

- 改进软件结构，提高模块独立性。
- 模块规模适中。
- 深度、宽度、扇入、扇出适当。
- 模块作用域应在控制域内。
- 模块接口简单。
- 尽量单入口、单出口。
- 模块功能应可预测。

扇出越大，模块控制越复杂；扇入高通常说明模块复用程度高。

### 5.9 界面设计

界面设计不仅是好看，还要让用户能稳定、低负担地完成任务。

原则:

- 以用户为中心。
- 保持一致性。
- 提供必要反馈。
- 支持撤销和错误恢复。
- 减少用户记忆负担。
- 保持界面简单。

经典黄金原则:

- 置用户于控制之下。
- 减少用户记忆负担。
- 保持界面一致。

## 6. 结构化设计方法

### 6.1 结构化设计 SD

结构化设计以模块为基础，依据 DFD 和数据字典把需求模型转换为软件结构。

基本思想:

- 自顶向下。
- 逐步求精。
- 模块化。
- 信息隐藏。
- 高内聚低耦合。

### 6.2 层次图与结构图

层次图描述模块的上下级层次调用关系，但不描述数据传递。

结构图在层次关系基础上增加模块之间的数据流和控制信息，更接近软件结构设计产物。

考试区分:

- DFD 是需求分析模型，强调数据如何流动。
- 结构图是设计模型，强调模块如何组织和调用。

### 6.3 变换分析法

变换流是数据经过输入、变换中心、输出的结构。

步骤:

1. 复审和精化 DFD。
2. 确定数据流类型。
3. 划分输入流、变换中心、输出流边界。
4. 做一级分解，形成主控模块、输入模块、变换模块、输出模块。
5. 继续二级分解。
6. 按启发式规则优化结构。

关键词: 输入、处理、输出。

### 6.4 事务分析法

事务流中存在事务中心，系统根据输入事务类型选择不同处理路径。

步骤:

1. 找到事务中心。
2. 找到各事务路径。
3. 建立接收事务、分派事务、处理事务的模块结构。
4. 细化每条事务路径。

关键词: 事务中心、分支选择、多条活动路径。

### 6.5 详细设计工具

详细设计要描述模块内部处理过程。常见工具:

- 程序流程图: 直观，但容易画出不良控制结构。
- N-S 图: 用盒状结构表示顺序、选择、循环，结构化强。
- PAD 图: 问题分析图，适合结构化过程描述。
- 判定表: 适合条件组合多、动作明确的逻辑。
- 判定树: 适合条件层次清楚的决策。
- PDL: 过程设计语言，用接近自然语言的伪代码描述处理过程。

考试常问: PDL 描述“怎么做”，需求规格说明不应写算法细节。

老师 2026 资料里更突出三个工具: 程序流程图、盒图 NS 图、判定树/判定表。尤其要会用盒图描写简单处理过程。结构化程序设计只使用顺序、选择、循环三种基本控制结构，并要求逐步求精、单入口单出口。

## 7. 软件实现

### 7.1 编码不是软件工程全部

实现阶段把设计转换成代码，但代码质量依赖前面的需求和设计。

编码目标:

- 正确实现设计。
- 可读。
- 可测试。
- 可维护。
- 遵守编码规范。

### 7.2 代码重用

重用可以发生在不同层次:

- 代码重用。
- 组件重用。
- 框架重用。
- 设计模式重用。
- 文档和测试用例重用。

重用要注意接口匹配、质量可靠、适应当前需求。

### 7.3 代码评审

代码评审是在运行测试前通过人工检查发现问题。

常查:

- 是否符合设计。
- 是否违反编码规范。
- 是否有边界条件错误。
- 是否有异常处理遗漏。
- 是否影响可维护性。

评审属于静态质量保证手段。

## 8. 软件测试

### 8.1 测试目的

软件测试的目的是发现错误，而不是证明程序没有错误。

重要原则:

- 测试只能证明有错误，不能证明没有错误。
- 应尽早测试。
- 测试用例应包含输入数据和预期输出。
- 程序员应避免只测试自己写的程序。
- 要重视边界和异常情况。
- 修改后要做回归测试。

老师 2026 资料的测试原则要额外背:

- 一般不测试自己设计的程序。
- 要对测试输入有预期输出。
- 要对合法输入和非法输入都进行测试。
- 测试数据应作为 SCI 纳入文档管理。
- 程序中的错误率和已经发现的错误数量成正比。

### 8.2 验证与确认

- 验证 Verification: 是否正确地构造产品，强调符合规格说明。
- 确认 Validation: 是否构造了正确的产品，强调满足用户真实需要。

简记: 验证看“做得对不对”，确认看“是不是用户要的”。

### 8.3 V 模型、W 模型、H 模型

V 模型把开发阶段和测试阶段对应起来:

- 需求分析对应验收测试。
- 概要设计对应系统测试。
- 详细设计对应集成测试。
- 编码对应单元测试。

W 模型强调测试活动应与开发活动并行开始，需求和设计也要测试。

H 模型强调测试活动是相对独立的流程，包括测试准备、测试执行、测试评估等。

### 8.4 白盒测试

白盒测试根据程序内部结构设计测试用例。

常见覆盖:

- 语句覆盖: 每条语句至少执行一次。
- 判定覆盖: 每个判定真假分支至少执行一次。
- 条件覆盖: 每个条件真假至少出现一次。
- 判定/条件覆盖: 判定真假和条件真假都覆盖。
- 条件组合覆盖: 每个判定中条件取值组合都覆盖。
- 路径覆盖: 尽可能覆盖独立路径。

覆盖强度通常: 语句覆盖较弱，路径覆盖较强。

### 8.5 环路复杂度

环路复杂度用于估计程序独立路径数。

常用公式:

```text
V(G) = E - N + 2
V(G) = 判定结点数 + 1
```

其中 E 是边数，N 是结点数。考试给流程图时，最稳妥是数判定结点，再加 1。

### 8.6 黑盒测试

黑盒测试不看内部代码，只根据输入输出规格设计测试。

常见方法:

- 等价类划分。
- 边界值分析。
- 因果图。
- 判定表。
- 错误推测。

### 8.7 等价类划分

等价类把输入域分成若干类，认为同一类中的数据揭示错误的能力相近。

步骤:

1. 找输入条件。
2. 划分有效等价类和无效等价类。
3. 为每个有效等价类设计测试用例。
4. 为每个无效等价类单独设计测试用例。

### 8.8 边界值分析

很多错误发生在边界附近，所以边界值分析重点测试最小值、最大值、刚小于边界、刚大于边界。

例如输入范围是 `1..100`，常测:

```text
0, 1, 2, 99, 100, 101
```

### 8.9 测试层次

- 单元测试: 测模块内部，依据详细设计。
- 集成测试: 测模块之间接口和协作。
- 确认测试: 验证软件是否满足需求。
- 系统测试: 把软件放到完整系统环境中测试。
- 验收测试: 用户参与，决定是否接受系统。
- 回归测试: 修改后重新测试，防止引入新问题。

老师资料的测试策略顺序是:

```text
单元测试 -> 集成测试 -> 系统测试 -> 验收测试
```

单元测试对象是模块，包含代码审查和动态测试。代码审查属于静态测试，动态测试根据测试用例运行程序。单元测试一般以白盒测试为主，之后其他测试以黑盒测试为主。

集成测试策略:

- 自顶向下: 需要桩模块。
- 自底向上: 需要驱动模块。
- 三明治集成: 上下结合。
- 大爆炸集成: 简单但定位错误困难。

### 8.10 α 测试和 β 测试

- α 测试: 用户在开发方控制环境下测试。
- β 测试: 用户在真实使用环境中测试。

二者都常出现在确认测试或验收前后的语境中。

### 8.11 调试

测试发现错误，调试定位并修复错误。测试和调试不是同一件事。

常见调试方法:

- 蛮力法。
- 回溯法。
- 原因排除法。

修复后要做回归测试。

## 9. UML 与面向对象基础

### 9.1 面向对象基本概念

- 对象: 具有状态和行为的实体。
- 类: 对一组相似对象的抽象。
- 属性: 对象状态。
- 操作/方法: 对象行为。
- 封装: 隐藏内部数据和实现。
- 继承: 子类复用和扩展父类。
- 多态: 同一接口在不同对象上表现出不同行为。

### 9.2 UML 是什么

UML 是统一建模语言，用图形化方式描述软件系统的结构和行为。它不是开发过程，也不是编程语言。

常见视图:

- 用例视图。
- 逻辑视图。
- 进程视图。
- 实现视图。
- 部署视图。

### 9.3 常见 UML 图

- 用例图: 表示参与者和系统功能。
- 类图: 表示类、属性、方法和类间关系。
- 对象图: 某时刻对象及链接。
- 顺序图: 强调消息时间顺序。
- 协作图/通信图: 强调对象协作关系。
- 状态图: 描述对象状态变化。
- 活动图: 描述业务流程或控制流。
- 包图: 表示系统组织结构。
- 构件图: 表示软件构件。
- 部署图: 表示运行节点和部署关系。

### 9.4 UML 关系

- 关联: 对象之间有结构联系。
- 聚合: 整体与部分，部分可独立存在。
- 组合: 强整体与部分，整体销毁部分也销毁。
- 泛化: 继承关系。
- 依赖: 一个元素使用另一个元素。
- 实现: 类实现接口。
- 包含 include: 一个用例必然使用另一个用例。
- 扩展 extend: 在特定条件下扩展基本用例。

考试常把 include 和 extend 混着考: include 是必做公共步骤，extend 是可选或条件扩展。

## 10. 面向对象分析 OOA 与设计 OOD

### 10.1 OOA 做什么

OOA 建立问题域模型，重点理解用户需求和领域对象。

主要模型:

- 用例模型。
- 静态模型。
- 动态模型。

老师 2026 资料列出的 OOA 过程:

1. 建立用例模型。
2. 确定类和对象。
3. 确定类属性。
4. 确定类服务。
5. 确定类结构。
6. 确定主题。
7. 建立动态模型。

### 10.2 用例模型

用例从用户视角描述参与者与系统的一次完整交互。

识别用例时注意:

- 从系统边界出发。
- 一个用例描述一个相对完整功能。
- 用例不是界面。
- 一个参与者可关联多个用例，一个用例也可关联多个参与者。
- 用例图不表达功能实现细节和逻辑过程。

### 10.3 静态模型

静态模型通过类图反映领域概念。任务是找类、对象、属性、服务和类间关系。

识别类的一般步骤:

1. 从需求描述中找候选名词。
2. 筛除外部实体、属性、操作、实现细节。
3. 确定类名、属性和服务。
4. 建立关联、泛化、依赖等关系。

### 10.4 动态模型

动态模型描述对象交互和状态变化。

常用图:

- 顺序图: 时间顺序。
- 状态图: 状态变化。
- 活动图: 流程。
- 协作图: 对象链接和消息。

若题目强调“对象之间消息传递顺序”，优先想到顺序图。

### 10.5 OOD 做什么

OOD 把 OOA 的问题域模型转换为可实现的设计方案，重点是系统设计和对象设计。

老师 2026 资料列出的 OOD 主要过程:

- 系统设计: 分层、分块、抽象。
- 类对象设计: 精化类的属性和方法、精化类间关系。
- 数据设计: 实体类与关系数据库的映射关系。
- 消息设计: 消息的类型和发送。
- 人机交互设计: 界面类、接口类的设计。

OOD 原则:

- 信息隐藏和模块化。
- 重用。
- 单一职责。
- 规划和统一接口。
- 优先使用聚合。
- 开放封闭原则。

优先使用聚合是因为继承会让子类强依赖父类修改，聚合更灵活。

### 10.6 常见设计模式

- Singleton 单例: 系统中只需要一个实例。
- Abstract Factory 抽象工厂: 创建一族相关对象而不指定具体类。
- Mediator 中介者: 用中介对象减少多个对象之间复杂依赖。
- Adapter 适配器: 把一个类接口转换成客户希望的接口。
- Iterator 迭代器: 顺序访问集合元素而不暴露内部结构。
- State 状态: 不同状态下表现不同行为，减少复杂分支。

考试通常问“某场景适合哪种模式”或“模式解决什么问题”。

### 10.7 面向对象测试

OO 测试以类为基础。

注意:

- 封装减少非法访问，但也增加内部状态观察难度。
- 继承会传播父类错误，子类重写方法后要重新测试。
- 多态让同一调用可能绑定到不同实现，要覆盖不同对象类型。

## 11. 软件维护

### 11.1 软件维护是什么

软件维护是软件交付使用后，为改正错误、适应环境变化、满足新需求或提高质量而修改软件的过程。

维护通常是生命周期中时间最长、工作量最大的阶段。

### 11.2 维护分类

- 纠错性维护: 修复运行中发现的错误。
- 适应性维护: 适应软硬件环境、数据环境变化。
- 完善性维护: 增强功能、提高性能、满足新需求。
- 预防性维护: 主动改进，提高未来可维护性和可靠性。

常见占比最大的是完善性维护。

### 11.3 结构化维护与非结构化维护

- 结构化维护: 有完整配置，包括需求、设计、代码、测试文档等，维护较容易。
- 非结构化维护: 只有代码或文档缺失，维护困难且风险高。

文档完整性直接影响可维护性。

### 11.4 维护过程

典型过程:

1. 提出维护申请报告 MRF。
2. 分析维护类型、范围、影响和成本。
3. 修改设计。
4. 设计复审。
5. 修改代码。
6. 测试和回归测试。
7. 复查、验收和更新文档。

维护不是随便改代码，而是一个简化的软件生命周期。

### 11.5 可维护性

影响可维护性的因素:

- 可理解性。
- 可测试性。
- 可修改性。
- 可移植性。
- 可重用性。

老师 2026 资料中优先列出的主要因素是前三个: 可理解性、可测试性、可修改性。可移植性和可重用性作为扩展理解。

提高可维护性的方法:

- 完整准确的文档。
- 良好模块化设计。
- 结构化程序设计或面向对象设计。
- 清晰编码规范。
- 维护性复审。

### 11.6 维护副作用

维护可能引入副作用:

- 修改代码的副作用。
- 修改数据的副作用。
- 修改文档的副作用。

所以维护后必须做回归测试，并同步更新文档。

## 12. 软件项目管理

### 12.1 项目管理目标

软件项目管理通过计划、组织、控制软件开发资源，让项目按质量、成本、进度要求完成。

目标:

- 如期完成任务。
- 成本控制在计划内。
- 妥善处理需求变动。
- 保证项目质量。
- 保持跟踪与控制。

项目管理难点常是人、成本和进度。

### 12.2 软件规模度量

软件度量分为:

- 直接度量: 直接统计软件属性，如代码行数 LOC。
- 间接度量: 通过多个因素估算，如功能点 FP。

LOC 常见指标:

```text
生产率 P = KL / E
每行代码平均成本 C = S / KL
文档与代码比 D = PG / KL
代码出错率 R = ER / KL
```

其中 KL 是千行代码，E 是工作量，S 是总开销，PG 是文档页数，ER 是错误数。

LOC 缺点:

- 依赖编程语言。
- 不利于鼓励简洁设计。
- 适合过程式语言，对早期估算帮助有限。

### 12.3 功能点 FP

功能点从用户可见功能角度估算规模。

五类信息域常见为:

- 输入项数。
- 输出项数。
- 查询数。
- 文件数。
- 外部接口数。

FP 相比 LOC 更适合早期估算，因为它不强依赖具体代码行数。

### 12.4 项目估算

常见估算方法:

- 类比已有项目。
- 经验公式。
- 按问题分解。
- 按过程分解。

估算不是一次性动作，需求和设计变化后要更新。

### 12.5 进度管理

甘特图:

- 直观看到任务起止时间。
- 不擅长表达任务之间复杂依赖和关键路径。

网络图:

- 能表达任务依赖。
- 可找关键路径和关键任务。
- 适合分析进度风险。

缩短开发时间通常会增加沟通成本和工作量，不是简单多加人就能解决。

### 12.6 CMM

CMM 软件能力成熟度模型把组织的软件过程能力分为五级:

1. 初始级。
2. 可重复级。
3. 已定义级。
4. 已管理级。
5. 优化级。

记忆方式: 从混乱个人经验，逐步走向可重复、标准化、定量管理和持续优化。

### 12.7 软件配置管理

配置管理控制软件开发过程中的各种配置项:

- 需求文档。
- 设计文档。
- 源代码。
- 测试用例。
- 用户文档。

核心概念:

- 配置项: 受控的软件产物。
- 基线: 经过正式评审并受控的配置版本。
- 版本控制: 管理不同版本。
- 变更控制: 控制修改申请、影响分析、批准和记录。

## 13. 高频考点清单

### 13.1 必背概念

- 软件 = 程序 + 数据 + 文档。
- 软件工程三要素 = 方法 + 工具 + 过程。
- 软件生命周期六阶段。
- 软件危机原因。
- 瀑布、原型、增量、螺旋、敏捷适用场景。
- SRS 作用和质量属性。
- DFD 四元素、父子图平衡、数据字典。
- 概要设计与详细设计区别。
- 高内聚低耦合。
- 内聚和耦合类型排序。
- 白盒与黑盒测试区别。
- 单元、集成、确认、系统、验收、回归测试。
- UML 常见图与关系。
- 维护四分类。
- LOC、FP、甘特图、网络图、CMM。

### 13.2 大题模板

需求分析题:

1. 先写系统边界和外部参与者。
2. 再列功能需求、非功能需求、数据需求。
3. 建 DFD 或用例图。
4. 说明 SRS 应保证正确、完整、一致、可验证。

DFD 改错题:

1. 查外部实体、加工、数据存储、数据流是否连线合法。
2. 查加工是否有输入和输出。
3. 查数据流是否命名。
4. 查父图与子图是否平衡。

设计原则题:

1. 先说明设计目标高内聚低耦合。
2. 再用模块化、抽象、信息隐藏解释。
3. 如果问问题，指出是哪类内聚或耦合。
4. 给出改进: 拆分职责、简化接口、减少全局数据、隐藏内部实现。

测试用例题:

1. 先判断白盒还是黑盒。
2. 白盒数判定结点求独立路径数。
3. 黑盒划分有效/无效等价类。
4. 边界题写边界内、边界上、边界外。
5. 每个用例写输入和预期输出。

UML 建模题:

1. 先定系统边界和参与者。
2. 用例图只画用户目标，不画界面步骤。
3. 类图找名词作候选类，筛掉属性和实现细节。
4. 顺序图按时间顺序写对象间消息。

维护题:

1. 判断维护类型。
2. 写维护申请和影响分析。
3. 修改设计、代码和文档。
4. 做回归测试。
5. 说明可维护性因素。
